Published the tool and the rest of the work, since it makes the numbers above checkable without my machine: **https://github.com/VIGO-VI/hellocam-linux** (GPL-2.0-or-later).

What is in it, in case any of it is useful for the record:

- `hellocamctl` — the tool that produced the measurements (single file, Python standard library only, no root, no udev rule). `hellocamctl doctor`, `xu`, `ir status|on|off`, `capture`, `mic`, `selftest` (11 checks, writes D1, captures, writes D0, captures, restores), `v4l2test`.
- `docs/FINDINGS.md` — the descriptor model, and the three-way split between "works out of the box / works only with help / firmware does not implement it".
- `kernel/` — an out-of-tree `uvcvideo` proof of concept in two patches (the face-authentication menu control, and a quirk dropping this camera's broken Region-of-Interest bits). `kernel/fetch-sources.sh` pulls the v7.3 sources rather than vendoring them; `pristine + patches` reproduces the tree that built. Those patches have not been sent anywhere.

*Correction, same day:* this comment originally described a "silent microphone behind a monitor hub" as a finding. That was wrong — the camera went back on the same hub and records audio after a physical replug. What differs between the silent and working states is a bus-power cycle, not the port, and `USBDEVFS_RESET` does not cut VBUS. The repo's `docs/FINDINGS.md` now says that.

*Correction, later the same day:* this comment originally reported a second finding — that `uvc_ctrls[]`'s Region of Interest entry was internally inconsistent (matching `bmControls` bit 21 while carrying selector `0x14`). That was my error, not the driver's. The Camera Terminal's `bmControls` ordering is not `selector - 1` for the UVC 1.5 additions: the driver's own table puts Focus Auto at bit 17 (selector 8), Privacy at bit 18 (selector `0x11`) and ROI at bit 21 (selector `0x14`), which matches the merged ROI implementation and its review. This camera advertising bit 21 is spec-compliant; the firmware is what fails, and only on its RGB terminal: `GET_CUR` on the ROI control answers `-EIO`, which `uvc_query_ctrl()` derives from the device's invalid-unit/control/request error codes, while the IR terminal's ROI control accepts `SET_CUR 1` and reads back 1. That is why the quirk is scoped to one interface rather than the device, and why a driver fix is not the answer.

One thing that does still stand, and is generic rather than NexiGo-specific: this camera returns only the count byte for `GET_MIN` on the MS-XU face-authentication control (observed; the Microsoft document says `GET_MIN` and `GET_RES` both do), while `uvc_query_ctrl()` asks for the full 9 bytes and logs "returned 1 bytes when we expected 9". Harmless, but it is noise a driver-sized control cannot avoid today.
